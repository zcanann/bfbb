Reading the catalog

What the labels mean

Player result
A concrete controller input produced an observed result in the running game. These populate the front-page matrix.
Lab-only result
The test tools forced part of the setup to answer “what would happen?” The effect is real, but a player cannot necessarily create it yet. These stay under Research leads.
End result verified
The game does something useful once the target value is present, but no normal gameplay setup is known to create that value.
Verified effect
The write changes the running game in a repeatable way.
No reward or access change
The state changed, but a matched control showed no different reward, unlock, warp, or area access.
Load blocker / crash
The sequence does not reach controllable play under the tested conditions.
Candidate
The predicted write overlaps something interesting, but its behavior has not been tested in the running game.

Are these all the same setup?

No. The basic player action is: build a combo, pause and quit before its reward appears, let that delayed screen animation begin on the title screen, then load a file. Different source maps and timings make it overwrite different parts of the next level.

Lab-only rows deliberately force part of that setup. A result such as “+49 shinies” proves what the game does after the write; it does not mean an unmodified run can reach that write.

What is the bug doing?

The combo reward animation starts late on the title screen. When the next level loads, the game accidentally keeps using memory from that old animation. Its next update can therefore overwrite an object in the newly loaded level.

The source map and exact combo timing decide what gets overwritten. Public summaries focus on the player action and result. Addresses, C++ fields, and memory-chain details remain available under each result’s collapsed Technical record.
